# Bug Reporter Filtering, Health Gate, and Endpoint Fixes

**Date:** 2026-05-06
**Status:** Approved (design phase)
**Source issues:** GitHub #78, #79, #80, #81 (all `auto-bug` label)

## Background

Four open GitHub issues, all auto-generated by the in-app reporter, share a common pattern: fetch failures (`Fetch is aborted` / `Load failed`) on `/device/connect`, `/device/scan-known`, and the transcript view. Investigation showed:

- **#80** (`Load failed`) fired because the Python backend hadn't started when the frontend made its first call. The 15s startup grace in `app/preload.js:56` did not catch it.
- **#78** (`renderer-unhandled | view:transcript`) is an unhandled promise rejection from the transcript poller's fetch — almost certainly a navigation-time abort, not a real fault.
- **#79** and **#81** are recurring `AbortError` cases from the 30s frontend timeout in `app/preload.js:32` and `app/tauri-bridge.js:32`. `/device/connect` realistically takes 5–45s for BLE pairing; 30s is borderline.
- The reporter (`app/main.js:229-435`) does not filter `AbortError` — every timeout or user-cancellation becomes a GitHub issue.

Of the four issues, zero to one represent real defects. The rest are reporter overreach.

## Goals

1. Stop filing GitHub issues for legitimate aborts and startup races.
2. Preserve diagnostic visibility — every suppressed error is still recorded locally.
3. Eliminate the Python-startup race by gating the UI on a health check.
4. Stop `/device/connect` from being incorrectly reported when BLE pairing legitimately runs long.
5. Suppress the transcript-view unhandled rejection.

## Non-goals

- `/device/scan-known` adapter recovery / retry logic — defer until local diagnostics show real evidence.
- Backend-enforced timeouts on BLE operations — defer.
- Frontend retry / exponential backoff — defer.
- Closing the four existing issues — handled out-of-band after a release ships with these fixes.

## Architecture

Three coordinated changes plus targeted endpoint fixes:

1. **Local diagnostics log** — new file-based sink under `<userData>/diagnostics.log` for suppressed errors. JSON-line format, 1 MB rotation, one backup.
2. **Reporter filters** — `AbortError` and "backend down" errors are routed to the diagnostics log instead of GitHub.
3. **Health gate** — frontend mounts a splash that polls `/health` until the Python backend responds, then mounts the main UI. The same poller continues at 5s cadence and feeds the reporter's "backend down" filter.
4. **Endpoint targets** — `/device/connect` joins `NO_TIMEOUT_ENDPOINTS`; the transcript-view setInterval poller wraps its fetch in try-catch.

## Components

### Diagnostics log (`app/main.js`)

- New helper `_appendDiagnostic({context, message, stack, fingerprint})`.
- File: `<userData>/diagnostics.log` (e.g., `~/Library/Application Support/Plaud V2/diagnostics.log` on macOS).
- One JSON line per event: `{ts, version, context, message, stackTruncated}`. Stack truncated to 4 KB.
- Rotation: when the active file exceeds 1 MB, rename it to `diagnostics.log.1` (overwriting any prior backup) and start fresh. Total disk ceiling ≈ 2 MB.
- Synchronous append on the main process side (low frequency, simpler than streams).

### Reporter changes (`app/main.js:229-435`)

- New predicates:
  - `_isAbortError(message)` — matches `/aborted|AbortError|signal is aborted/i` (case-insensitive).
  - `_isBackendDown()` — reads `lastHealthState` updated by the health poller (default `up` until first failure observed).
- Reporter flow becomes: fingerprint → check filters → if either matches, call `_appendDiagnostic` and return; otherwise existing GitHub flow runs (and also calls `_appendDiagnostic` so the local log is complete).
- Existing dedupe and 15s startup grace can be removed once health-gate is in place — they exist to paper over the same race.

### Health gate (frontend)

- New module `app/ui/health-gate.js`.
- On startup, renders a minimal splash (logo + spinner + "Starting backend…") and polls `GET /health` every 250 ms.
- After 30s without success, replaces splash with a "Backend not responding" screen offering **Retry** (restarts the splash + 30s poll cycle) and **Open diagnostics log** (opens the file in the OS default app).
- After success, mounts the main UI and starts a slower 5s background poller. The poller pushes its current state (`'up' | 'down' | 'unknown'`) to the main process via IPC (Electron) or a Tauri command. The main process stores it as `lastHealthState`; `_isBackendDown` reads that variable directly.
- Removes the existing 15s startup grace from `app/preload.js:56` and `app/tauri-bridge.js`.

### Endpoint fixes

- **`/device/connect` timeout.** Add to `NO_TIMEOUT_ENDPOINTS` in both `app/preload.js:19` and `app/tauri-bridge.js:19`. Matches existing treatment of `/device/sync`. Backend Bleak handles its own timing; if it hangs indefinitely, behavior matches existing `/device/sync` (user restarts app).
- **Transcript poller (`app/ui/transcript.js:837`).** Wrap the setInterval `await window.plaud.transcripts()` call in try-catch. On `AbortError`, no-op silently. On other errors, `console.warn` (the global `window.onunhandledrejection` handler still routes them through the reporter, which now filters appropriately). Audit the audio fetches on lines 145 and 1190 — both already have `.catch()` per investigation; verify, do not widen.

### `/health` endpoint

If absent in the Python backend, add a trivial route returning `{ok: true, version}`. Confirm in `app/routes/` before assuming new code is needed.

## Data flow

```
App launch
  ├─ Main process spawns Python subprocess (existing)
  ├─ Renderer loads → mounts health-gate.js (splash visible)
  └─ Health-gate polls /health every 250 ms (cap 30 s)
       ├─ OK   → mounts main UI
       │        starts 5 s background poller
       │        reporter filter reads backendHealth
       └─ FAIL → "Backend not responding" + Retry + "Open diagnostics log"

Error occurs
  ├─ Captured by global handler / IPC / API wrapper
  ├─ Fingerprinted (existing)
  ├─ FILTER: AbortError? → diagnostics log only
  ├─ FILTER: backendHealth=down? → diagnostics log only
  └─ Otherwise → diagnostics log AND GitHub
```

## Error-handling matrix

| Error source | Filter outcome | Sink |
|---|---|---|
| `AbortError` from any fetch | Suppressed | Diagnostics log |
| Network error while `backendHealth=down` | Suppressed | Diagnostics log |
| Network error while `backendHealth=up` | Reported | GitHub + log |
| API returns existing transient marker | Suppressed | Existing behavior preserved |
| API returns non-transient `data.error` | Reported | GitHub + log |
| Renderer unhandled rejection | Filtered same as above | GitHub or log |
| Main-process uncaught exception | Reported | GitHub + log |

## Edge cases

- **Python crashes mid-session.** 5 s background poller flips `backendHealth` to `down` within 5 s; reporter switches to log-only for follow-up failures. Splash does **not** re-appear; existing in-app toasts handle the user-facing message.
- **Disk quota.** 2 MB ceiling for diagnostics log is negligible.
- **`/device/connect` in `NO_TIMEOUT_ENDPOINTS`.** If Bleak hangs forever the request hangs forever. Matches existing `/device/sync` behavior; acceptable.
- **First-launch grace.** Existing 15 s startup grace becomes redundant and is removed.

## Testing strategy

Manual only — the reporter spans `window`, file system, and child processes; mocking would cost more than it catches.

1. **Cold start, slow Python.** Inject a 5 s sleep in Python startup → splash visible ~5 s, UI mounts, no reports.
2. **Python never starts.** Break Python startup → splash times out at 30 s, "Backend not responding" + Retry shown. Diagnostics log has entries; GitHub has none.
3. **AbortError on navigation.** Call `/device/connect`, navigate away mid-flight → no GitHub issue, one diagnostics-log line.
4. **Real backend error.** Force `/transcribe` to raise a non-transient exception → GitHub issue created, diagnostics log also recorded.
5. **Mid-session Python crash.** Kill Python process while app running → toasts appear on next call, no GitHub issue, diagnostics log captures.
6. **Log rotation.** Pre-write a 1.1 MB diagnostics log → next append rotates to `.log.1`.
